# ADR 0005: Skills share through build-time classes

- **Status**: Accepted
- **Date**: 2026-11-16

## Context

Apart from a few skills that point into another skill's files (eks-operation-review into apex's runbooks, ecs-modernize into terraform-skill, and others), nothing is shared between our skills today: no shared folders, no symlinks, no check that compares copies. Rules every skill should follow, such as "use MCP, fall back to the CLI", are written separately in the router, `rules/AGENTS.md` and several skills, in different words. The same tool lives as several copies that drift apart: there are four `tools/report_to_html.py` files, in ecs-operation-review, eks-cost-intelligence, eks-ingress-migration and eks-operation-review. A fix to one rule has to land in every copy by hand.

The next major version wants one source of truth: change one place and it changes everywhere, and a skill copied out alone still keeps its rules and tools.

The [Agent Skills](https://agentskills.io/) format has no inheritance. File references are relative paths from the skill root, and there is no import or dependency field. Claude Code's `${CLAUDE_SKILL_DIR}` points only at the skill's own folder, Kiro's GitHub import copies one skill folder, and our installer treats every folder under `skills/` as a skill. The only thing every harness agrees on is files physically inside the skill folder.

We weighed and dropped four other ways to share: symlinks, a shared base skill read at run time, rules kept only in the router, and a shared package. Each breaks on a skill copied out alone, a Kiro import or a plugin cache, or leaves a lone skill without its safety rules.

[ADR 0004](0004-naming.md) rejected "parent and child" as names partly because "Skills inherit nothing". With classes, skills do inherit, so that reasoning no longer holds.

Until now the repo kept its vendor sync scripts and added no tooling that copies files from one place into many. Classes need exactly that tooling.

Earlier documents answered one of two questions and left the other open: when the contributor skill for new skills is built (step 7, in ADR 0002 and the design notes), and what happens to a skill held by an outside owner who does not take up v2. This record answers the first. For the second it sets only how owners are asked; what a decline does to the skill is not decided here.

## Decision

**Classes.** Shared rules, tools, schemas and evals live in classes, one folder per class under `classes/`, outside `skills/` so the installer never treats a class as a skill. A build script, `misc/sync-classes.py`, copies each class's files into every member skill. CI runs it with `--check` and fails on any difference, so a hand edit of a copy is caught. Each copied file carries a header that names the class file it came from and says not to edit it. A skill names its classes in its frontmatter metadata.

**What this supersedes.** This record replaces the "Skills inherit nothing" reasoning of ADR 0004. ADR 0004's decision stands: `apex` is the entry skill, and every other skill is a standalone knowledge or solution skill. A standalone skill still does not depend on `apex` at run time; it inherits its classes' rules and tools at build time, as copies inside its own folder. ADR 0004 is not edited.

**Cross-copy tooling.** Copying shared files into many skills is now a core part of the design, so the repo now adds such tooling. The website copy of each skill is already generated by `misc/update-pages.sh`, which has its own `--check`, so it is not made a second class-sync target. The DevOps Agent ports are rewritten for their own runtime, so a straight copy does not fit them; how they take class changes is planned later in step 3, once more of the base is built.

**When the contributor skill is built.** ADR 0002 and the design notes said the contributor skill for new skills is built in step 7. This record replaces that: `apex-new-skill` is built in step 3, before any skill moves to the classes, as a member of the class for skills that maintain the repo. It reads `classes/` rather than hard-coding them, and it is fixed in the same step whenever building the skills shows it is wrong. ADR 0002 is not edited.

**Skills held by outside owners.** eks-upgrade-check, eks-operation-review, eks-well-architected-review and eks-ingress-migration are held by outside owners. Each owner gets one full issue describing how the skill would join the classes, and the owner decides how to proceed. The rebuild does not wait on an owner's answer. The fixes we found for that skill stay written in its issue.

## Consequences

- One rule or tool is written once and reaches every member skill in one pull request, with CI proving every copy matches.
- A skill copied out alone keeps its domain knowledge, its class rules and its tools. It loses only routing, runbooks and hand-offs ([ADR 0003](0003-standalone-skills-are-a-weaker-tradeoff.md) accepts the runbook loss), and any hook installed outside the skill folder.
- A class change shows one diff per member skill, so class pull requests are large.
- Every sentence moved into a class is copied into every member, so classes stay small, and a class that turns out to share nothing is not built.
- A class check proves a rule's text landed, not that the skill obeys it. Rules such as read-only and no Secret reads also need evals.
- A copy a customer took earlier does not update itself; its header names the class file to compare against.
- Vendor sync scripts replace a vendored skill's folder on each pull, so for an owner who accepts, the class files are written by the sync, after the pull.
- `rules/AGENTS.md` goes once its rules are in the base class, and [ADR 0001](0001-runbooks-live-in-apex.md) is revisited as the runbooks are absorbed into the classes and the skills.
- The wider reasoning is in the [skill design notes](../design/skill-design.md#classes).
