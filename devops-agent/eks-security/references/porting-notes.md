# Porting Notes: eks-security

This file documents the differences between the Claude Code version and the DevOps Agent port. It is for maintainers, not for the agent to read during execution.

> **Staleness check:** the table below describes the upstream skill at a point in time and can drift as `skills/eks-security/` evolves. Re-verify each row against upstream when materially changing either copy, and update the date here. Last verified: 2026-11-05 (port rebuilt for the three review capabilities; the knowledge references re-copied from upstream at that date).

## Differences from Claude Code Version

| Aspect | Claude Code version | DevOps Agent version |
|--------|--------------------|--------------------|
| **Execution model** | Interactive: asks the discovery questions conversationally; runs bundled scripts for the three reviews | Fully autonomous, no interactive prompts (as the port SKILL.md states): resolves missing context from cluster state or documented defaults and notes each assumption; a fact it cannot read is reported `unknown` with what to supply, never a stop to ask |
| **Review capabilities (C1 CVE and advisory review, C2 security event response, C3 posture check)** | Scripted: `collect.sh`, `advisory_fetch.py`, `advisory_check.py`, `match.py`, `posture_*.sh`, `render_report.py` in `assets/` | The same three capabilities as procedures the agent walks with read-only Agent Space reads. No scripts (DevOps Agent runs the non-executable subset only). Parity is in the record schema, the component catalog (copied into `cve-advisory-review.md` as a table) and the verdict rules, which are word for word in the port SKILL.md and `cve-advisory-review.md` |
| **C1 advisory side** | `advisory_fetch.py` reads the feeds; `advisory_check.py` verifies each quoted line in code | The agent reads the feed or page, or the text the team supplies, and applies the same quote, catalog and range checks before comparing. An advisory it cannot read makes every targeted component `unknown`. Whether a given Agent Space can reach the public feed hosts depends on its configuration |
| **C3 posture check** | Scripted: 64 checks `SEC-POSTURE-1` to `64` (1 to 54 adapted from eks-well-architected-review's security pillar, 55 to 64 added containment checks), reduced to a score, a coverage gate and seven layer verdicts; a manual, unscripted repository check list | The containment subset as procedures, under the same `SEC-POSTURE` ids, rules, scoring rule and layer-verdict rule (computed over these 20 checks, so the score is not comparable with the scripted 49-check score), plus two port-only rows (node role, image admission) reported outside the score. The rest of the copied pillar and the repository list (no file access in the Agent Space) are not ported; the report lists them under "not checked" |
| **Discovery** | 8 questions before any hardening recommendation | 3 items resolved from cluster context or defaults (regime, sensitivity, OS/AMI); 5 more gathered when depth allows |
| **Tool access** | Bash, kubectl, AWS CLI, optional MCP server | AWS APIs and Kubernetes APIs available in the Agent Space (read-only) |
| **Escalation** | Recommends engaging the AWS account team | Recommends engaging AWS Professional Services or Solutions Architects |
| **Skill routing** | Routes to sibling skills (eks-best-practices, eks-well-architected-review, eks-upgrade-check, eks-recon, eks-genai, eks-build) | Self-contained; names the alternative guidance domain without routing |
| **Script execution** | Runs its own read-only scripts; prints changes for the team | Advisory only: recommends commands for the user to execute |
| **MCP dependencies** | May use the EKS MCP server for the same reads | No MCP dependencies; uses Agent Space APIs directly |
| **Kubernetes access** | kubeconfig plus the `eks-security-reader` ClusterRole bound through an access entry with a Kubernetes group | The Agent Space access entry (associated with `AmazonAIOpsAssistantPolicy` by `devops-agent/setup.sh`) plus the same ClusterRole, bound by adding a Kubernetes group to that entry (`read-only-access.md`) |
| **Knowledge references** (15 hardening and compliance files) | Upstream copies | Copies of upstream as of 2026-11-05. Two keep port wording: `engagement-and-response.md` (autonomous "checks" instead of "questions", Professional Services escalation, no sibling routing) and `image-supply-chain.md` (one sentence). Edit both copies together |
| **Auto Mode security reference** | `references/auto-mode-security.md` | In sync; security facts are launch-agnostic. Edit both copies together |
| **Compliance references** | 4 per-regime deep files plus `compliance-regimes.md` | At full parity, byte-identical. Keep the compliance facts in sync across both copies |

## Change log

- **2026-11-05: three review capabilities.** Added `cve-advisory-review.md`, `security-event-response.md`, `posture-check.md`, `advisory-sources.md` and `read-only-access.md`, each adapted from its upstream file: script commands replaced by the reads the agent makes and by printed commands; record schema, catalog, verdict rules, report wording and the worked example kept. Why: the port has to give the same verdict as the Claude Code skill without running its scripts.
- **2026-11-05: event response.** `security-event-response.md` replaces the old incident response and forensics reference (deleted), as upstream did: one seven-step workflow for any event (scope, a quick record, contain at once, snapshot and investigate, remediate, verify, report), pod-scoped containment by label instead of a namespace-wide deny. Checking whether an exposure was exploited is not covered yet in either copy (issue 351).
- **2026-11-05: IAM.** `iam-policy.json` gains the reads the new procedures use, each taken from upstream `read-only-access.md`: `eks:DescribeAddonVersions`, `ListNodegroups`, `DescribeNodegroup`, `ListInsights`, `DescribeInsight`, `DescribePodIdentityAssociation`; `ec2:DescribeLaunchTemplateVersions`; `ecr:DescribeRepositories`, `DescribeImages`, `GetRegistryScanningConfiguration`, `DescribeImageScanFindings`; `inspector2:BatchGetAccountStatus`, `ListCoverage`, `ListFindings`; `iam:ListAttachedRolePolicies`, `ListRolePolicies`; and `eks:ListAssociatedAccessPolicies` for the access-entry admin check (`SEC-POSTURE-64`, upstream C3). The existing hardening reads stay. The SKILL.md Kubernetes access row no longer lists `podsecuritypolicies` (the API was removed in Kubernetes 1.25).
- **2026-11-05: execution model.** This file previously said the port stops at HARD STOP gates while the port SKILL.md said it never prompts. The SKILL.md is right: the port runs fully autonomously, applies defaults with stated assumptions, and reports unreadable facts as `unknown`. The table above now says so.
- **2026-11-05: dated facts.** SKILL.md Auto Mode, Pod Identity and guardrail facts re-checked to upstream's 2026-11-05 wording.
