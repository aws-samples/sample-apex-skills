# Runner trial: score sheet (pass or fail)

Repo line cites are at commit 7efa0776.

The sheet compares three candidate runners on the same seven cases (cases.md). No row needs a runner to win, and the sheet itself picks none. The pick, C1, is written in results.md (Pick): it rests on S6 alone and waits on the user's acceptance; the rule below is met as written.

What "pass" means: the trial passes when every cell S1 to S10 is filled for all three candidates (a measured value, a value read from the tool or code where the cell says so, the S10 estimate, 'cannot run (why)' or 'n/a (why)'), and results.md states the pick with its reasons from S2, S6 and S10; otherwise it fails. It fails if any candidate the pick names has no measured S2 n/3, or if a pick reason rests on a 'cannot run' or 'n/a' cell. A case's own pass is its condition in cases.md, counted per run in S2.

Candidates C1 to C3: README.md. C1's extension is sized against the runner at 7efa0776, not built, in this trial (results.md), except two pieces the trial's driver does itself (old against new by git archive, and three runs); C2 is `claude plugin eval` in Claude Code 2.1.328 (the version every C2 run's output records).

## Facts settled before the runs

- **Adapters.** C1's Kiro and Codex adapters are sized against the runner at 7efa0776, not built, in this trial: the files are in results.md. Kiro CLI 3.3.0 (read 2026-11-16; 3.4.0 on 2026-11-19) has a headless mode (`kiro-cli chat --no-interactive`, `--output-format stream-json`), and Codex CLI 0.163.0 has one (`codex exec --json`). Both are driven directly for T1.
- **C2 target.** `claude plugin validate` rejects a bare skill folder (`claude plugin validate <skill dir>` prints "No manifest found in directory. Expected .claude-plugin/marketplace.json or .claude-plugin/plugin.json" and exits 1); `claude plugin eval` accepts a path, but the trial uses a wrapper so validate and eval read the same manifest. A wrapper folder outside the repo, holding `.claude-plugin/plugin.json` (name, version, description) and `skills/<skill>`, prints "Validation passed with warnings" and exits 0. It warns that no author is set, and its plugin-directory checks list README_MISSING, LICENSE_MISSING and ICON_MISSING, which do not affect eval. C2 runs on such a wrapper, with `--no-publish` so the HTML report stays local (publishing to claude.ai is "already the default when your account supports it", claude plugin eval --help, under --publish-report).
- **C3 account and cost.** C3 runs in an account in us-west-2 (the priced Region), through the on-demand Evaluate API only (`POST /evaluations/evaluate/{evaluatorId}`, with the spans passed in `evaluationInput.sessionSpans`). It creates no resource. Batch and online evaluation, datasets and CloudWatch Transaction Search are not used: Transaction Search is an account-wide setting that switches all span ingestion, which a trial should not change. AWS documents this API only for spans first ingested into CloudWatch with Transaction Search enabled (getting-started-on-demand.html; supported-frameworks-telemetry.html step 1). It scores spans never ingested: one Evaluate call on one converted run scored on 2026-11-21 (results.md, Runs). The cost is in cost-estimate.md.
- **Skill evaluators.** AgentCore also has two skill evaluators, `Builtin.SkillSelectionAccuracy` and `Builtin.SkillInstructionFollowing`, which detect a skill from two trace signals, a read of its SKILL.md file or a framework's native skill-loading tool, with Claude Agent SDK among the frameworks listed for the second (https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/skill-evaluators.html, read 2026-11-19); they fit this repo's skill cases.
- **Judges.** C1's grader is a second `claude -p` on the same model as the subject (misc/evals/scripts/run_task_evals.py:581 `run_grader`, model passed at :612; default model `global.anthropic.claude-opus-4-6-v1`, :1025 and misc/evals/Makefile:35). C2's judge is Haiku by default ("--judge-model <model> Override LLM-grader model (default: haiku)"). C3 uses AgentCore's built-in evaluators, whose model cost is included in the evaluator price ("Model usage costs are included for built-in evaluators", https://aws.amazon.com/bedrock/agentcore/pricing/).
- **AgentCore pricing.** cost-estimate.md.
- **Moving the runner.** The trial also weighs moving the runner's dependencies out of the vendored skill-creator folder. That is not a score row; the recommendation is in results.md.

## C2 cases

Each case becomes one `case.yaml` under the wrapper's `evals/` folder (`claude plugin eval --help`: "<eval dir>/**/case.yaml or prompt.md + graders/*.md").
- Arms: `--ablation with-without`, the with-skill and no-plugin arms.
- Gated tools: `--allow-tools Bash` for T3 (the validator) and T7 (the cluster read), and `Write` for T2 and T3, which write their output to disk.
- Fixtures: T1's and T2's files are copied into the workspace by each case's `scaffold_script`, which runs only with `--scaffold`.
- T3: no C2 grader runs a script, so its pass is validate_project.sh run by hand on each kept workspace (`--keep-temp`).
- T5: cannot run (no multi-turn option in `claude plugin eval --help`).
- T7: `--help` names no kubeconfig option, so the read-only kubeconfig is set as `KUBECONFIG` in the environment of the `claude plugin eval` call; whether the child run reads it is recorded in S1. C2's T7 gets no per-run cluster session (S9), so its S1 and S2 cells are not comparable with C1's on setup.
- The wrapper's `plugin.json` holds `name`, `version` and `description`, and its `skills/` holds the one skill under test.
