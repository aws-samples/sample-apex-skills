# Contributing to APEX

This guide explains how the repository is organized, where new content should go, and the process for submitting contributions.

---

## Repository Architecture

APEX organizes content into four directories, each serving a distinct purpose in the agentic workflow. Understanding the distinction is critical — putting content in the wrong place degrades the agent's performance.

```
sample-apex-skills/
├── skills/             → 📚 WHAT the agent knows (domain knowledge)
│   └── apex/runbooks/  →   🎯 HOW the agent runs an engagement (guided procedures, routed by the apex skill)
├── rules/              → 📏 Project-level agent rules (AGENTS.md for consumers)
├── devops-agent/       → Non-executable ports for AWS DevOps Agent
└── examples/           → 🏗️ HOW to try it (hands-on exercises)
```

---

## `skills/` — Domain Knowledge

**Purpose:** Self-contained packages of specialized knowledge that the AI agent loads on demand. Skills follow the [Agent Skills open standard](https://agentskills.io/).

**Think of skills as:** An expert's brain — the accumulated knowledge, decision frameworks, and best practices that a senior SA carries. The agent consults this knowledge regardless of what task it's performing.

### Characteristics

- **Reusable across workflows** — the same `eks-best-practices` skill is used whether the agent is designing a new cluster, reviewing an existing architecture, planning an upgrade, or troubleshooting an issue
- **Stateless** — no conversation flow, no "ask the user this, then do that." Pure knowledge.
- **Triggered by description match** — the agent reads the `description` field in SKILL.md frontmatter and decides whether to activate the skill based on the user's request
- **Progressive disclosure** — SKILL.md contains the essentials (~500 lines max), `references/` contains deep-dive material loaded only when needed

### Structure

```
skills/{skill-name}/
├── SKILL.md              # Required: frontmatter (name, description) + body
├── references/           # Optional: detailed reference docs (loaded on demand)
│   ├── topic-a.md
│   └── topic-b.md
├── scripts/              # Optional: executable code for deterministic tasks
└── assets/               # Optional: files used in output (templates, etc.)
```

> **Naming:** Prefix skill names with the target service (`eks-`, `ecs-`) for auto-grouping in docs and README. Non-service skills use a descriptive name without prefix.

> **DevOps Agent ports:** DevOps Agent ports retain the same skill name and live under `devops-agent/` (not `skills/`). Constraints: no scripts, no Bash — markdown only.
>
> **Report footers:** upstream report templates in `skills/` keep a runtime-neutral footer ("generated by an APEX skill"); DevOps Agent ports set the footer to their target runtime ("generated by an AWS DevOps Agent skill").


### What Belongs in Skills

| ✅ Belongs | Example |
|-----------|---------|
| Decision frameworks | Compute selection matrix (Karpenter vs MNG vs Auto Mode vs Fargate) |
| Best practices | Security essentials (IAM, Pod Identity, PSA, network policies) |
| Reference tables | Upgrade sequence rules (control plane → add-ons → data plane) |
| Code patterns | Terraform module patterns and naming conventions |
| Quick wins | Cost optimization table (Graviton, Spot, consolidation) |

### What Does NOT Belong in Skills

| ❌ Does not belong | Why | Where it goes |
|-------------------|-----|---------------|
| "Ask the user these 8 phases of questions" | That's a conversation flow | `skills/apex/runbooks/<skill>/` |
| A Terraform module that deploys a cluster | That's runnable infrastructure | `examples/` |
| A deploy.sh script that sets up a demo | That's a hands-on exercise | `examples/` |
| Checkpoint templates with STOP gates | That's agent behavior control | `skills/apex/runbooks/<skill>/` |

### Current Skills

See the auto-generated [Skills Reference](README.md#skills-reference) in `README.md` — regenerated from each `skills/<name>/SKILL.md` frontmatter by `misc/update-skills-references.sh` (and enforced by CI via `misc/update-all-references.sh`), so it can't fall out of sync with the repo.

## `skills/apex/runbooks/`: Runbooks

**Purpose:** Guided procedures that control how the agent runs an engagement for one skill: sequencing steps, gathering requirements, enforcing checkpoints, and validating output.

**Think of a runbook as:** A senior SA's playbook: not what they know (that's skills), but how they run an engagement. The structured questionnaire they follow, the checkpoints they enforce, the quality gates they apply before delivering recommendations.

### Characteristics

- **Defines interaction patterns**: questionnaires, step-by-step procedures, STOP gates, checkpoint templates
- **References skills for knowledge**: a runbook says "use the `eks-best-practices` skill's decision frameworks" but does not duplicate the knowledge
- **One skill per folder**: each runbook lives in `skills/apex/runbooks/<skill>/` and is followed with that skill
- **Routed by the apex skill**: [`skills/apex/SKILL.md`](skills/apex/SKILL.md) detects intent, picks the skill and, when `runbooks/<skill>/` has a runbook for the task, follows it. Only the apex skill points at runbooks; other skills' SKILL.md files do not, except the vendored `eks-operation-review`, whose sync script points it at `../apex/runbooks/eks-operation-review/eks-operation-review.md` (the one recorded exception; see its UPSTREAM.md). Start with `/apex`.

### Structure

```
skills/apex/
├── SKILL.md                                   # Router: intent detection, routing, shared rules, hand-offs
└── runbooks/
    ├── eks-build/eks-build.md                 # Day 1: Cluster build and provisioning
    ├── eks-design/design.md                   # Day 0: Architecture questionnaire + quality check
    ├── eks-genai/eks-genai.md                 # Day 1: GenAI and LLM workloads
    ├── eks-operation-review/eks-operation-review.md  # Day 2: Operational health review
    ├── eks-platform-engineering/eks-platform-engineering.md  # Day 1: Internal Developer Platform
    ├── eks-security/eks-security.md           # Day 1/2: Hardening and compliance
    └── eks-upgrade-check/eks-upgrade-check.md # Day 2: Upgrade readiness assessment
```

### Why Router + Runbooks (Not Monolithic)

1. **Context efficiency**: the agent loads only the relevant runbook, not all of them
2. **Independent iteration**: improve the upgrade runbook without touching design
3. **Clear ownership**: different SAs can own different runbooks
4. **Shared context**: the apex skill carries context between skills (design decisions inform upgrade planning)

### What Belongs in a Runbook

| ✅ Belongs | Example |
|-----------|---------|
| Questionnaires | The 8-phase design questionnaire (Phase 1: Project Context → Phase 8: Confirm & Generate) |
| Pre-flight checklists | Upgrade pre-flight with STOP gates ("STOP if blocking PDBs found") |
| Quality gates | Scoring rubric (80% threshold across Well-Architected pillars) |
| Checkpoint templates | "✅ Step N complete. Validation: ... Ready for Step N+1?" |
| Mandatory warnings | "Once the control plane is upgraded, you CANNOT roll it back" |
| Conditional branches | "Terraform detected? → Terraform path. CLI-managed? → CLI path." |

Intent routing ("user says 'upgrade my cluster' → `eks-upgrade-check`") belongs in the apex skill's routing tables, not in a runbook.

### What Does NOT Belong in a Runbook

| ❌ Does not belong | Why | Where it goes |
|-------------------|-----|---------------|
| EKS best practices content | That's domain knowledge | `skills/` |
| Terraform code patterns | That's domain knowledge | `skills/` |
| A deployable Terraform module | That's runnable infrastructure | `examples/` |

### The Key Test

If you removed all runbooks, would the agent still *know* the right answers? **Yes**: skills provide the knowledge. But the agent wouldn't know *how to run the engagement*: it wouldn't follow the questionnaire, enforce checkpoints, or validate output quality.

## `examples/` — Hands-On Exercises

**Purpose:** Deployable, runnable scenarios that demonstrate APEX workflows in practice. They include infrastructure code, planted issues, test scripts, and documented test results.

**Think of examples as:** A workshop lab: the actual environment where someone can deploy infrastructure, run APEX against it, and see the agent in action. Examples are how we validate that runbooks + skills actually work, and how we deliver workshops to customers.

### Characteristics

- **Runnable** — `deploy.sh` creates infrastructure, `destroy.sh` tears it down
- **Self-contained** — each example includes everything needed to run the exercise
- **Demonstrates a runbook**: each example maps to a runbook (e.g., an example demonstrating `skills/apex/runbooks/eks-design/design.md`)
- **Contains planted issues** — realistic problems for the agent to discover and fix
- **Documents test results** — conversation logs showing how the agent performed, with issue tables and fix tracking
- **Used for iteration**: test results drive improvements to runbooks (test-01 → fix the runbook → test-02)

### Structure

```
examples/{scenario}/{variant}/
├── README.md              # Required: frontmatter (name, description, workflow) + exercise guide
├── manifests/             # Kubernetes manifests (planted issues, test resources)
├── scripts/
│   ├── deploy.sh          # Deploy the exercise environment
│   └── destroy.sh         # Clean up everything
├── static/                # Screenshots, diagrams
└── tests/
    ├── test-01.md         # Full conversation log from test run 1
    └── test-02.md         # Full conversation log from test run 2
```

Each example's `README.md` must include YAML frontmatter:

```yaml
---
name: EKS Upgrade Readiness
description: Assess cluster upgrade readiness across 8 dimensions with a scored report.
workflow: skills/apex/runbooks/eks-upgrade-check/eks-upgrade-check.md
---
```

- `name` — short label (required)
- `description` — one-line summary (required)
- `workflow`: which runbook this example demonstrates (optional)

### What Belongs in Examples

| ✅ Belongs | Example |
|-----------|---------|
| Deployable infrastructure | Terraform that creates an EKS 1.30 cluster |
| Planted issues | Kubernetes manifests with deprecated APIs, blocking PDBs, stale RBAC |
| Deploy/destroy scripts | `deploy.sh` that sets up the exercise environment |
| Test conversation logs | Issue tables (what went well, what failed, fixes made) |
| Screenshots | Agent behavior during test runs |

### What Does NOT Belong in Examples

| ❌ Does not belong | Why | Where it goes |
|-------------------|-----|---------------|
| Best practices documentation | That's domain knowledge | `skills/` |
| Conversation flow definitions | That's agent orchestration | `skills/apex/runbooks/` |
| Generic reference material | That's skill reference content | `skills/{name}/references/` |

## Creating a New Skill

Steps:

1. Understand the skill with concrete examples. A skill for an AWS service with no skills here yet: open an issue first; it needs maintainer changes to grouping and the docs sidebar.
2. Plan reusable contents (scripts, references, assets).
3. Hand-author `skills/<name>/SKILL.md` and any `references/` / `agents/` / `scripts/` / `assets/` subdirectories (no scaffolding script exists — see [`skills/skill-creator/SKILL.md`](skills/skill-creator/SKILL.md)).
4. Scaffold `misc/evals/<name>/` with `cd misc/evals && make init-evals SKILL=<name> [SIBLINGS="a,b"]` (see misc/evals/README.md), then expand `triggering.json` to ≥16 prompts (≥8 positives, ≥8 near-miss negatives).
5. Update every neighbour's sibling map and triggering.json using `python misc/evals/scripts/update_sibling_map.py`, one call per neighbour. A neighbour shares vocabulary or domain; zero neighbours is valid; skill-creator and terraform-skill are upstream-synced and excluded, and `apex` (the router, which has no eval folder) is excluded too.
6. Fan out: add the routing row in [`skills/apex/SKILL.md`](skills/apex/SKILL.md) and any hand-written catalogue, then run `./misc/update-all-references.sh` (it regenerates `skills/README.md` and the README tables; never edit those blocks by hand) and `./misc/update-pages.sh`. `git add` the new files first: `update-pages.sh` reads the git index (`git ls-files`) and skips untracked files.
7. Package: `python skills/skill-creator/scripts/package_skill.py skills/<name>`.

### Pre-PR checklist for new skills

Verify each item before opening the PR.

- [ ] `skills/<name>/SKILL.md` present with valid frontmatter
- [ ] `misc/evals/<name>/triggering.json` has ≥16 prompts (≥8 positives, ≥8 negatives)
- [ ] Every neighbour's `SIBLING_MAP` block in `misc/evals/<neighbour>/README.md` lists this new skill, and the corresponding negatives are in `misc/evals/<neighbour>/triggering.json`
- [ ] Catalogue entries landed: the routing row in `skills/apex/SKILL.md` and any hand-written catalogue, then `./misc/update-all-references.sh` run (it regenerates `skills/README.md`)

### Keeping skill docs in sync after changes

Adding, renaming, or removing a skill — or editing a SKILL.md frontmatter description — should be followed by running the `update-docs` skill so wrappers, marker blocks, and prose references stay in sync. The skill walks both script-managed surfaces (`update-all-references.sh`, `update-pages.sh`) and hand-written prose, proposing diffs for anything stale.

## Creating a New Runbook

1. Create `skills/apex/runbooks/<skill>/<name>.md`, in the folder of the skill it runs with (every runbook is named after its folder except `eks-design/design.md`)
2. Add a header naming the lifecycle and the skill: `> **Lifecycle:** Day <n>` and `> **Skill:** <skill>`
3. Do not add a routing table: the apex skill's tables route (five of the moved runbooks, eks-build, eks-design, eks-genai, eks-platform-engineering and eks-security, still carry one; a later change removes them; the runbooks for the two vendored skills, eks-operation-review and eks-upgrade-check, keep a `## Routing` section on scope)
4. Structure as phases with numbered checklists and STOP gates
5. Check that a routing row in `skills/apex/SKILL.md` sends the request to that skill
6. Run `./misc/update-all-references.sh` and `./misc/update-pages.sh` to update `skills/README.md` and the site. `git add` the new files first: `update-pages.sh` reads the git index (`git ls-files`) and skips untracked files.
7. Test with a real scenario and document results in `examples/`

## Keeping docs in sync (auto-generated catalogues)

Two catalogues in the repo are **auto-generated** from each entry's frontmatter and must not be edited by hand:

| Block | Rendered in | Source of truth | Regenerator |
|---|---|---|---|
| Skills Reference | `README.md`, `skills/README.md` | `skills/<name>/SKILL.md` frontmatter | `misc/update-skills-references.sh` |
| Examples Reference | `README.md` | `examples/**/README.md` frontmatter | `misc/update-examples-references.sh` |

Each block is delimited by HTML markers like `<!-- SKILLS_REFERENCE_START -->` / `<!-- SKILLS_REFERENCE_END -->`. The regenerator owns everything between the markers; anything outside them is free.

**One-shot refresh** (run this whenever you add a skill, runbook, or example, or change a frontmatter field):

```bash
./misc/update-all-references.sh
```

The generator scripts (including `./misc/update-pages.sh`) parse frontmatter with PyYAML, so running them locally requires it: `pip install pyyaml`.

**CI enforcement.** The `docs-sync` job in `.github/workflows/docs-sync.yml` reports a status on every PR event once its workflows are allowed to run (none run while a PR has merge conflicts, and a PR from someone outside both this repository and its organization waits until someone with write access approves the run), but it does real work only when the PR changes a path the workflow watches; otherwise it is a no-op that passes. The `eval set hygiene` and `validate` checks (`.github/workflows/evals.yml`, `.github/workflows/devops-agent-validate.yml`) work the same way: green on a PR that touches none of their watched paths means not needed, not tested. The real work is `./misc/update-all-references.sh --check` and `./misc/update-pages.sh --check`. If the rendered blocks or Docusaurus wrappers diverge from frontmatter, the job fails and prints the exact diff. The fix is always the same: run both commands locally, commit the result.

CI also strict-parses `SKILL.md` frontmatter via `misc/validate-frontmatter.py` before regenerating. The frontmatter must satisfy all of these rules:

- it is a valid YAML mapping between `---` delimiters
- `name` and `description` are present, and `description` is at most 1024 characters
- only these top-level keys are allowed: `name`, `description`, `license`, `metadata`, `allowed-tools`
- no YAML anchors or aliases (`&name` / `*name`)
- the frontmatter block is under 64KB
- nesting depth is at most 8

These rules make the repo's frontmatter a compliant subset of the [Agent Skills specification](https://agentskills.io/specification): every allowed key is a spec field, and the spec's optional `compatibility` field is rejected here.

For `skills/` each description must also match the generated `skills.json` manifest (`devops-agent/` is exempt from the manifest check; a missing manifest entry is only a warning). If validation fails, fix the frontmatter YAML and rerun the regeneration commands above.

## Creating a New Example

1. Create `examples/<scenario>/<variant>/`
2. Add `README.md` with frontmatter (`name`, `description`, `workflow`) and exercise guide (overview, prerequisites, setup, expected outcome)
3. Add `scripts/deploy.sh` and `scripts/destroy.sh`
4. Add planted issues in `manifests/` or infrastructure code
5. Run the exercise with APEX and document results in `tests/`
6. Use test results to iterate on the corresponding runbook
7. Run `misc/update-examples-references.sh` to update the README

## Reporting Bugs / Feature Requests

We welcome you to use the GitHub issue tracker to report bugs or suggest features.

When filing an issue, please check existing open, or recently closed, issues to make sure somebody else hasn't already
reported the issue. Please try to include as much information as you can. Details like these are incredibly useful:

* A reproducible test case or series of steps
* The version of our code being used
* Any modifications you've made relevant to the bug
* Anything unusual about your environment or deployment


## Contributing via Pull Requests

Contributions via pull requests are much appreciated. Before sending us a pull request, please ensure that:

1. You are working against the latest source on the *main* branch.
2. You check existing open, and recently merged, pull requests to make sure someone else hasn't addressed the problem already.
3. You open an issue to discuss any significant work - we would hate for your time to be wasted.

To send us a pull request, please:

1. Fork the repository.
2. Modify the source; please focus on the specific change you are contributing. If you also reformat all the code, it will be hard for us to focus on your change.
3. Ensure local tests pass.
4. Commit to your fork using clear commit messages.
5. Send us a pull request, answering any default questions in the pull request interface.
6. Pay attention to any automated CI failures reported in the pull request, and stay involved in the conversation.

**Installer changes:** run the installer tests first. `install-paths.sh` runs the installer against a local fixture repository with `HOME` pointed at a scratch directory; CI runs it on pull requests that change `misc/installer/**` or a `skills/*/SKILL.md` file. Before a review of an installer change, also run the mutation check (manual; weekly in CI): it fails if any deliberately broken copy of `bin/cli.mjs` passes the tests. A full run can take hours; rerun one mutant with `--only <ID>`.

```bash
misc/installer/test/install-paths.sh          # source tree
misc/installer/test/install-paths.sh --pack   # the packed tarball
misc/installer/test/mutate.sh                 # mutation check
```

GitHub provides additional document on [forking a repository](https://help.github.com/articles/fork-a-repo/) and
[creating a pull request](https://help.github.com/articles/creating-a-pull-request/).


## Releasing to npm

From installer 1.3.0 on, a merged skill or runbook change reaches `npx apex-skills` users at the next release tag, not at merge: the installer installs the newest `v1.x.y` release tag, not `main`. Installer 1.2.0 and earlier follow `main`: a default install clones it and `--update` runs `git pull` on it, so their users get a merged change at their next install or `--update`. Installer 1.3.0 was released by **Installer 1.3.0 (tag first)** below; later v1 releases use steps 1 to 7.

1. Run `./misc/bump-version.sh <version>` (e.g. `./misc/bump-version.sh 1.2.0`)
2. Commit the version bump
3. Open a pull request with the bump and merge it (main takes changes only through pull requests)
4. Create a GitHub Release tagged `v<version>` targeting main (this also creates the tag; a Release whose target is not `main` is skipped by the workflow and publishes nothing to npm, but installer 1.3.0 and later still install its tag when it is the newest `v1.x.y`: they read every tag of the repository, on any branch, with or without a Release). Mark it as a pre-release to publish to npm's `next` tag instead of `latest`; the mark only chooses the npm tag: installer 1.3.0 and later install a new `v1.x.y` tag (one with no `-`) as soon as it exists, marked or not
5. The `release-npm.yml` workflow auto-publishes to npm via OIDC trusted publisher: to `next` when the Release is marked pre-release or the version contains `-`, else to `latest`
6. Verify: `npm view apex-skills dist-tags` shows the new version on the expected tag
7. To promote a version from `next` to `latest`, an npm owner of the package runs `npm dist-tag add apex-skills@<version> latest` by hand (the workflow never does)

**Pre-releases:** Tags containing `-` (e.g. `v1.3.0-rc.0`) publish to the `next` dist-tag too. `bump-version.sh` takes `X.Y.Z` only (it also rewrites the `--version` examples in the docs, which must name a release), so for such a version set `"version"` in `misc/installer/package.json` by hand (e.g. `1.3.0-rc.0`), commit, and create the GitHub Release `v1.3.0-rc.0` marked as a pre-release.

**Installer 1.3.0 (tag first):** Done for v1.3.0 (kept as the record of the pre-promotion state; Rollback below cites it): merge the pull request with `misc/installer/package.json` at `1.3.0` on main (set by hand in that pull request, not with `./misc/bump-version.sh`, which would also rewrite the `v1.2.0` examples of `--version` in README.md, getting-started.md and misc/installer/README.md; they stay on v1.2.0), then right away create the GitHub Release `v1.3.0` targeting main, marked as a pre-release, with the backup line from the "Before upgrading from installer 1.2.0 or earlier" sentence of `misc/installer/README.md` in its release notes (tick the pre-release box before you publish the Release: the workflow runs once, when the Release is published, and without the mark it puts 1.3.0 on `latest` at once; ticking it afterwards changes nothing on npm. If that happens, an npm owner points `latest` back with `npm dist-tag add apex-skills@1.2.0 latest` and `npm dist-tag add apex-skills@1.3.0 next`, so `npx apex-skills@next` still tests it. This moves only the tag: an install made with 1.3.0 in between stays a 1.3.0 install, and a later 1.2.0 run over it can replace its Kiro copies marked `inclusion: manual`, edited ones included, with steering links (a clone 1.3.0 made from scratch stays on `v1.3.0`; one that 1.3.0's `--update` moved from `main` can be pulled to main's tip, and `npx apex-skills@1.3.0 --update` moves it back; when that 1.2.0 clone was made after main had moved past the `v1.3.0` commit, 1.2.0's `git pull --ff-only` fails instead (exit code 1, "Git pull failed", with advice to remove `~/.apex-skills`) and nothing is rewritten). To remove an install that 1.3.0 made, run `npx apex-skills@1.3.0 --uninstall` (if installer 1.2.0 ran over it (a plain `npx apex-skills` before 1.3.0 reached `latest`, or `npx apex-skills@1.2.0`), run `npx apex-skills@1.3.0 --update` first, or `--uninstall` keeps the links 1.2.0 rewrote, exit code 3): installer 1.2.0's `--uninstall` usually leaves that install's skill links and always leaves `~/.claude/apex-steering` and the Kiro steering copies. Then run `npm view apex-skills dist-tags`). That one step creates the release tag `v1.3.0` (the content a plain `npx apex-skills` installs once 1.3.0 is promoted to `latest`; until then a plain install runs 1.2.0, which follows `main`) and publishes installer 1.3.0 to `next`, once. Test it with `npx apex-skills@next`, with `@next` on every command (until the promotion a plain `npx apex-skills`, every command the installer prints included, such as `--update` and `--branch main`, runs 1.2.0, which, when it installs steering for Kiro CLI, replaces 1.3.0's Kiro copies, edited ones included, with steering links), then promote the same version: `npm dist-tag add apex-skills@1.3.0 latest`. After the promotion, remove the "Release order" paragraph and the sentence that starts "While installer 1.3.0 is on npm's `next` tag" from `misc/installer/README.md` (the 1.3.0 package's README keeps this text until a later version is published), remove the paragraph that starts "This describes installer 1.3.0." from `README.md` and `misc/website/docs/getting-started.md`, and the "(`@next` before promotion, as above)" note after it, drop "or `@next` before promotion; " from each "to remove an install that 1.3.0 made" sentence, matched case-insensitively (README.md, getting-started.md, misc/installer/README.md, and this paragraph and the Rollback paragraph below), drop the parenthetical "(npm `latest` is 1.2.0 until 1.3.0 is promoted to it)" at the top of this section, and edit the GitHub Release `v1.3.0` to clear its pre-release mark.

**v2.0.0:** its release notes must say how to install APEX v2: v1 installs print a note pointing at https://github.com/aws-samples/sample-apex-skills/releases once a `v2.0.0` or later release tag exists (pre-release tags such as `v2.0.0-rc.0` do not count; the `v2.0.0` tag does, even if its GitHub Release is marked pre-release).

**Rollback:** moving an npm tag changes which installer a plain `npx apex-skills` runs and rolls back no release tag: installer 1.3.0 and later install the newest `v1.x.y` tag and 1.2.0 clones `main`, so for a bad release tag release a fixed, higher `v1.x.y`. Moving `latest` to 1.2.0 brings back the Kiro copy risk in the Installer 1.3.0 paragraph. To move `latest` back to the previous version, an npm owner runs `npm dist-tag add apex-skills@<previous version> latest` (installs made with the newer version are not undone: to remove an install that 1.3.0 made, run `npx apex-skills@1.3.0 --uninstall` (if installer 1.2.0 ran over it (a plain `npx apex-skills` before 1.3.0 reached `latest`, or `npx apex-skills@1.2.0`), run `npx apex-skills@1.3.0 --update` first, or `--uninstall` keeps the links 1.2.0 rewrote, exit code 3): installer 1.2.0's `--uninstall` usually leaves that install's skill links and always leaves `~/.claude/apex-steering` and the Kiro steering copies); to warn the users of a bad version, `npm deprecate apex-skills@<version> "reason"` + publish a patch.
