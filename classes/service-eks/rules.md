# Service EKS rules

A service-eks skill reads an Amazon EKS cluster. These rules bind every Kubernetes read to the cluster the user named. They tighten `apex.read-only-unless-confirmed` and `apex.mcp-first`, never loosen them.

- **service-eks.ask-for-context**: Ask the user which kubeconfig context reaches the target cluster; never pick one from the current context or from a context's name alone. Add no kubeconfig entry of your own: no `aws eks update-kubeconfig`, `kubectl config set-context` or other kubeconfig write. If no context reaches the cluster, stop and ask the user to add the target's kubeconfig entry. This tightens the `update-kubeconfig` allowance in `apex.read-only-unless-confirmed`.
- **service-eks.preflight**: Before the first Kubernetes read on the kubectl route, run `scripts/service_eks_preflight.py check --cluster <name> --region <region> --context <ctx>` (add `--kubeconfig <file>` when the user named one), with one `--read <verb>:<resource>[:<namespace>]` for each read this skill's own read list needs. It checks that the context exists, records the current context, compares the context's server with the endpoint from `aws eks describe-cluster` (a context alias with a matching endpoint is accepted), and runs an `auth can-i` check for each read. On exit 2, show the user its `message` and read nothing from that cluster: a `no` or an error from any `auth can-i` check stops the run and names each missing verb and resource. Do not warn and carry on.
- **service-eks.context-on-every-read**: Every kubectl read line this skill runs or prints carries `--context <verified-context>`, the context the preflight checked, examples and permission probes included. A sentence saying "add `--context` everywhere" does not replace the flag on the line. Lines in `references/` that the user runs are marked customer-run and are not checked.
- **service-eks.record-and-restore**: The preflight records the current context and never switches it. A step that does switch the context follows `apex.read-only-unless-confirmed`: tell the user, and at the end run `scripts/service_eks_preflight.py restore --recorded <recorded_context>`, which switches back, or tells the user which context is now set when there was none.
- **service-eks.mcp-binding**: Name the Amazon EKS MCP Server first, as `apex.mcp-first` says, with the AWS CLI and kubectl as the fallback. Before the first Kubernetes request through the MCP server, match the connection to the intended cluster's ARN or its endpoint from `aws eks describe-cluster`, and stop if the binding cannot be verified. The kubectl fallback runs through `service-eks.preflight`.
- **service-eks.least-privilege**: The reads a skill passes to the preflight are the least access it needs, read verbs only (`get`, `list`, `watch`), never Secrets (`apex.no-secrets`). When a read is denied, point the user to an EKS access entry: the EKS Best Practices Guide maps the access policy `AmazonEKSViewPolicy` to the Kubernetes `view` role and asks for least privileged access (https://docs.aws.amazon.com/eks/latest/best-practices/identity-and-access-management.html, sections "Cluster Access Manager", "Employ least privileged access to AWS Resources" and "Employ least privileged access when creating RoleBindings and ClusterRoleBindings", source `github.com/aws/aws-eks-best-practices` `latest/bpg/security/iam.adoc`, checked on 2026-11-17). The guide does not cover choosing or checking the kubeconfig context, so the context rules above come from APEX's own design (`apex.eks-guide-first`).
