# Router rules

A router skill picks the skill for a request, carries context between skills, suggests what could help next and follows the customer's runbooks. Each routed skill owns its own procedure; do not re-implement it here. The tables these rules use are in `references/router-routing.md`.

- **router.decides-route**: When this router is loaded, it decides the route, even if another skill's description also matched the request. Load only the skill it routes to for the current step (a row that names two skills loads them together). If another skill already loaded for this request and the route here differs, name both skills and ask the user which to use; if the route is the skill already loaded, carry on with it. If the conversation began in another skill without this router, apply these rules from the point this router loads.
- **router.most-specific-row**: Pick the most specific row in the routing tables; a catch-all row applies only when no more specific row fits. When more than one row fits, break the tie in this order: the most specific row first, then the stage hint, then one question that names both skills.
- **router.route-steps**: Route in this order. (1) Named skill: if the request names a skill, route to it at once with no questions, and still infer the stage from that choice; if it is not installed, say so, then route by the steps below. (2) Read first: the request, anything the user gave or pointed to, and the workspace files that bear on the route; read local files only, discovery runs no account or cluster calls; skip every question these already answer. (3) One clear match: route at once; do not ask "what would you like to do?" (4) Ask only what is missing, grouped in one turn, then follow the tie-break order. (5) No row matches: follow the catch-all rows in the routing tables. (6) Say the route in one line: the skill, why, and the stage when you know it.
- **router.stage-as-hint**: Infer the customer's stage (Day 0 Design, Day 1 Build, Day 2 Operate) from the request, the files and any skill they named. Use it only to break a tie between two equally specific rows, to pick discovery questions and to pick next skills. Never rule out a skill because its family differs from the stage you inferred.
- **router.carry-context**: When one skill leads to another, carry forward the context the hand-off table lists; do not re-ask it. If the user already did the earlier step, cite its decisions; if not, the next skill gathers the minimum it needs. Use what you learn about the customer's work only to route, carry context and suggest next skills; send it to no system beyond what the routed skill's own steps call.
- **router.suggest-never-run**: Suggest next skills only after a skill this router routed to has finished, and only when a natural next step exists: one line, 1 to 3 skills from its hand-off row that fit the customer's stage, each with a few words on why. Never load or run a suggested skill until the user asks. When nothing fits, suggest nothing.
- **router.runbooks**: A runbook is the customer's own procedure that chains skills: which skills, in what order, what to carry between them and the customer's own gates. Runbooks live in this skill's `runbooks/` folder; the `example-*.md` files there are dummy examples to copy and adapt, followed only when the user names one. Follow a runbook step by step: one skill per step, the context the hand-off table lists carried between steps, each skill's own rules applied; a runbook may only tighten a safety rule (`apex.tighten-only`). While a skill's own procedure still sits in `runbooks/<skill>/`, follow it with that skill when a request routes there and the folder has a runbook for the task. Name a runbook only after you have found its file. For work that spans several skills with no runbook, chain them by the routing and hand-off tables.
